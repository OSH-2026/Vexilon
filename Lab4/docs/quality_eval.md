# 模型输出质量评估

## 1. 质量评估目标

本次质量评估旨在：
- 评估 Qwen2.5-0.5B-Instruct（Q4_K_M 量化）在 5 类不同任务上的输出质量
- 对比不同采样参数（temp / top-p）对输出质量的影响
- 为后续实验选择合理的推理参数提供依据
- 记录 0.5B 量化小模型在各类任务上的真实表现和局限性

## 2. 模型与量化格式

| 项目 | 说明 |
|---|---|
| 模型名称 | Qwen2.5-0.5B-Instruct |
| 参数量 | 0.5B |
| 量化格式 | Q4_K_M（4-bit 量化，中等质量） |
| 模型文件 | `models/qwen2.5-0.5b-instruct-q4_k_m.gguf` |
| 模型大小 | 约 469 MB |

## 3. Prompt 设计

本次评估设计了 5 个 prompt，覆盖 5 类不同任务：

| ID | 类别 | 主题 | 选择原因 |
|---|---|---|---|
| P1 | 中文问答 | 进程与线程的区别 | 测试模型对操作系统核心概念的掌握和中文表达能力 |
| P2 | 摘要 | 虚拟内存/页表/TLB/缺页中断技术材料 | 测试模型的信息提取和归纳能力 |
| P3 | 代码解释 | C 代码（含 bug）的功能和问题分析 | 测试模型的代码理解和错误诊断能力 |
| P4 | 推理题 | 贴错标签的盒子（经典逻辑谜题） | 测试模型的逻辑推理和逐步分析能力 |
| P5 | 课程相关 | mmap/共享库/CoW 的关联与区别 | 测试模型对 OSH 课程核心知识点的综合理解 |

**类别覆盖检查：** 中文问答、摘要、代码解释、推理题、课程相关问题（全部 5 类）

## 4. 配置对比

| 参数 | configA（较高随机性） | configB（较低随机性） |
|---|---|---|
| threads | 2 | 2 |
| ctx-size | 2048 | 2048 |

| top-p | 0.9 | **0.8** |
| repeat-penalty | 1.1 | 1.1 |
| n-predict | 256 | 256 |

**差异说明：** configA 使用较高温度（0.7）和较高 top-p（0.9），鼓励模型生成更多样化的输出；configB 使用较低温度（0.2）和稍低 top-p（0.8），使输出更确定、更保守。两组配置的 threads 均限制为 2，原因是本机 CPU 散热有限，更高线程数已经导致过载关机。

## 5. 评分标准

| 维度 | 字段 | 含义 | 评分范围 |
|---|---|---|---|

| 幻觉程度 | `hallucination_level` | 是否出现虚构事实、编造函数/概念等 | 低/中/高 |

## 7. 每类 prompt 的具体分析

### 7.1 P1 中文问答：进程与线程的区别

**configA 输出摘要：** 将进程定义为"独立运行的程序实例"，线程定义为"特殊的进程实例"（概念混淆）。提到进程有独立内存空间、线程也有自己的内存空间（错误：线程共享进程内存空间）。在 IPC 部分仅提到 shell 调用和 C/C++ 程序调用，未涉及管道、共享内存、消息队列等实际 IPC 机制。输出在最后一个要点处被截断（达到 256 token 限制）。

**configB 输出摘要：** 结构更清晰，将进程和线程分别按编号说明。但同样存在严重事实错误：声称线程拥有"自己的地址空间"（错误：同一进程的线程共享地址空间）。IPC 部分列出了信号量、管道、共享内存，但描述较简略。输出也被截断。

**质量对比：** 两组配置的核心问题相同——模型对"线程共享进程地址空间"这一基本概念理解错误。configB 的结构稍好，但 correctness 没有实质改善。这反映了 0.5B 模型的知识容量限制，而非采样参数问题。

### 7.2 P2 摘要：虚拟内存技术材料

**configA 输出摘要：** 提取出 5 个要点：虚拟内存提供独立地址空间、页表实现映射、TLB 加速转换、CPU 通过 TLB 处理缺页中断、虚拟内存支持 CoW。第 4 点表述不够精确（CPU 是"先查 TLB，TLB miss 后查页表，页表项不在内存中才触发缺页中断"，而非"通过 TLB 查找最近使用的页表项"来处理缺页）。

**configB 输出摘要：** 5 个要点更精炼准确：虚拟内存提供独立虚拟地址空间、页表实现映射、TLB 是硬件缓存、缺页中断由访问不在物理内存中的页面触发、虚拟内存支持 CoW 和 mmap 优化。每条一句话，表述更规范。

**质量对比：** 这是 5 个 prompt 中表现最好的类别。摘要任务相对容易——模型只需从给定材料中提取信息。configB 的低温输出更精确、更克制；configA 在要点 4 上有轻微表述偏差。P2 的成功说明模型在信息提取方面有一定能力，前提是所需信息已包含在 prompt 中。

### 7.3 P3 代码解释：C 代码 bug 分析

**configA 输出摘要：** 声称代码功能是"将字符串每个字符复制一次并返回"（错误理解：实际是反转字符串）。指出两个"bug"：（1）strlen() 未定义（错误：已包含 `<string.h>`）；（2）memcpy 语法错误（幻觉：代码中根本没有 memcpy）。"修复"代码中仍然缺少 null 终止符，且未提及内存泄漏。

**configB 输出摘要：** 正确识别功能为"复制并反转字符串"。指出内存泄漏（`malloc` 后未 `free`）和溢出风险。但给出的修复方案仍然不完整——未指出 `malloc(len)` 应为 `malloc(len + 1)`（缺少 null 终止符的空间），也未说明 `buf` 需要以 `\0` 结尾才能用 `%s` 打印。

**质量对比：** configB 明显优于 configA——至少正确描述了代码功能并识别了内存泄漏。configA 出现了严重的幻觉（编造了不存在的 memcpy 调用）。两组都未识别出最关键的 bug（缺少 null 终止符导致 `%s` 打印时可能读到越界数据）。真实 bug 列表：① `malloc(len)` 应为 `malloc(len + 1)`；② 未添加 null 终止符；③ 未调用 `free(result)`。

### 7.4 P4 推理题：贴错标签的盒子

**configA 输出摘要：** 严重偏离题目要求。声称要从每个盒子依次取出水果（违反"只能从一个盒子拿"的规则）。推理过程完全错误：认为三次取水果的结果都是"苹果和橙子混合"，逻辑不自洽。未得出正确答案。

**configB 输出摘要：** 尝试系统分析，但推理方向错误。断言"第一个盒子应该是橙子"，但未说明从哪个盒子取水果。后续推理混乱：声称"剩下的两个盒子应该都是苹果"（该问题中只有一个盒子装苹果）。未给出确定性的正确结论。

**质量对比：** 这是 5 个 prompt 中表现最差的类别。两组配置均未能正确解答。P4 的正确答案是：从贴"苹果和橙子混合"标签的盒子取水果——如果取出苹果，则该盒子实际是苹果，贴"苹果"标签的盒子实际是橙子，贴"橙子"标签的盒子实际是混合。如果取出橙子则相反。0.5B 模型在纯逻辑推理任务上的能力严重不足，这是一个清晰的局限性信号。

### 7.5 P5 课程相关：mmap / 共享库 / Copy-on-Write

**configA 输出摘要：** 将 mmap 描述为"将内存分配给特定进程，然后在该进程中读写该内存"（不准确：mmap 是将文件或匿名内存映射到进程地址空间）。共享库被描述为"特殊的内存映射工具"，CoW 完全没有独立展开说明。三个概念的协同关系未有效阐述，缺页中断的角色仅在 mmap 部分有微弱涉及。

**configB 输出摘要：** 错误更严重：将 mmap 描述为"将内存映射到磁盘"（方向反了：是文件映射到内存）。将共享库加载混淆为 IPC 机制。CoW 描述为"并发编程模型"并与 mmap 完全混淆——输出的 CoW 段落与 mmap 段落几乎相同。三个概念之间的真实关系（fork + CoW + mmap 协同实现高效共享库加载）完全未触及。

**质量对比：** 两组都出现了严重的概念混淆。configA 的表述更模糊但幻觉相对少；configB 在低温下给出了更"自信"的错误陈述。P5 揭示了 0.5B 模型在需要跨知识点关联的任务上的根本性局限——模型没有足够的知识容量来准确区分这些相关但不同的概念。

## 8. 不同 temp / top-p 对输出的影响

### 8.1 高 temp（configA, temp=0.7, top-p=0.9）

- **发散性：** 输出内容更丰富，但更容易引入事实错误。P3 编造了不存在的 `memcpy` 调用，P4 推理链条更长但完全错误。
- **幻觉倾向：** 明显更高。高温下模型更"大胆"地生成看似合理但实际错误的内容。
- **语言流畅性：** 中文表达流畅，但信息密度较低。
- **适用场景：** 可能适合创意写作类任务，但不适合需要准确性的技术问答和推理。

### 8.2 低 temp（configB, temp=0.2, top-p=0.8）

- **确定性：** 输出更简洁、更确定。P2 摘要的 5 个要点每条一句话，干净利落。
- **重复性：** 在 P5 中出现了明显的内容重复——CoW 段落与 mmap 段落几乎完全相同，这在低温下是一个典型问题。
- **正确性：** 在简单任务（如摘要）上正确性略优于 configA，但在复杂任务上没有实质改善。
- **适用场景：** 更适合需要确定性和简洁输出的场景，但无法弥补模型本身的知识缺陷。

### 8.3 综合判断

对于 0.5B 量化模型：
- temp 差异影响的是输出的**形式**（简洁 vs 丰富、确定 vs 发散），而非**实质正确性**
- 两类配置均存在严重的知识性错误和幻觉，区别在于低温下错误更"自信"，高温下错误更"多样"
- 温度降低**不能**修复模型本身缺乏的知识——线程不拥有独立地址空间、mmap 是文件到内存的映射，这些事实模型无论什么温度都搞错了

## 9. 结论

### 9.1 配置稳定性

**configB（低 temp）更稳定。** 输出更简洁、可预测、重复性可控。对于需要确定性输出的任务（如摘要），configB 略优。但"更稳定"不等于"更正确"——两组配置在事实准确性上没有本质区别。

### 9.2 配置发散性

**configA（高 temp）更发散。** 输出更长、更多样，但也更容易产生幻觉。在 P3 中编造了不存在的函数，在 P4 中推理链条更长但逻辑全错。对于创意类任务或许更合适，但对于本实验的技术类任务不甚理想。

### 9.3 各类任务难度排序

从模型表现看，任务难度从低到高：

| 难度 | 任务类型 | 表现 | 说明 |
|---|---|---|---|
| 低 | 摘要（P2） | 较好 | 信息已在 prompt 中，只需提取和重组 |
| 中 | 中文问答（P1） | 一般 | 基本框架正确但细节多处有误 |
| 中 | 代码解释（P3） | 较差 | 识别了部分问题但遗漏关键 bug，且有幻觉 |
| 高 | 课程相关（P5） | 差 | 概念混淆严重，无法建立正确关联 |
| 高 | 推理题（P4） | 很差 | 完全无法完成逻辑推理任务 |

### 9.4 0.5B 量化小模型的局限性

1. **知识容量不足：** 0.5B 参数量限制了模型存储精确知识的能力。进程/线程区别、mmap 原理等 OS 核心概念出现事实错误。
2. **逻辑推理能力缺失：** 在贴标签盒子问题上完全失败，无法进行多步推理。
3. **概念边界模糊：** 在 P5 中，mmap、共享库加载、CoW 三个相关概念被严重混淆，说明模型无法精确区分相近但不同的概念。
4. **幻觉严重：** 尤其在高温配置下，模型会编造不存在的函数（memcpy）、给出错误定义（线程是特殊的进程实例）。
5. **输出截断：** 256 token 的生成限制对于需要详细解释的 P1 和 P5 不足，输出常在不完整处截断。
6. **量化损失：** Q4_K_M 量化可能进一步降低了模型的准确性。
7. **适用建议：** 该模型可能仅适合简单问答和信息提取类任务。对于需要精确知识、逻辑推理或跨概念关联的任务，建议使用 7B 或更大模型。

## 10. 复现命令

### 10.1 环境准备

```bash
# 确认模型文件存在
ls -la models/qwen2.5-0.5b-instruct-q4_k_m.gguf

# 确认 llama-cli 可执行
ls -la llama.cpp/build/bin/llama-cli.exe

# 确认 prompt 文件完整
cat prompts/quality_prompts.jsonl
```

### 10.2 运行 configA（较高随机性）

```bash
python scripts/run_quality_eval.py \
  --config-name configA \
  --threads 2 \
  --temp 0.7 \
  --top-p 0.9 \
  --ctx-size 2048 \
  --n-predict 256
```

### 10.3 运行 configB（较低随机性）

```bash
python scripts/run_quality_eval.py \
  --config-name configB \
  --threads 2 \
  --temp 0.2 \
  --top-p 0.8 \
  --ctx-size 2048 \
  --n-predict 256
```

### 10.4 查看结果

```bash
# 查看 CSV
cat results/quality_eval.csv

# 查看原始输出
ls results/raw_quality_outputs/

# 查看某个输出文件
cat results/raw_quality_outputs/configA_P1.txt
```

### 10.5 脚本关键参数说明

| 参数 | 说明 | 默认值 |
|---|---|---|
| `--config-name` | 配置标签（必填） | 无默认值 |
| `--threads` | CPU 线程数 | 2 |
| `--ctx-size` | 上下文大小 | 2048 |
| `--temp` | 温度 | 0.7 |
| `--top-p` | Top-p 采样 | 0.9 |
| `--repeat-penalty` | 重复惩罚 | 1.1 |
| `--n-predict` | 最大生成 token 数 | 256 |
| `--timeout` | 单次推理超时（秒） | 120 |
| `--model-path` | 模型文件路径 | `models/qwen2.5-0.5b-instruct-q4_k_m.gguf` |
| `--llama-cli` | llama-cli 路径 | `llama.cpp/build/bin/llama-cli.exe` |
| `--prompts` | Prompt 文件路径 | `prompts/quality_prompts.jsonl` |
| `--output` | 输出 CSV 路径 | `results/quality_eval.csv` |

### 10.6 注意事项

1. **线程数限制：** 本机 CPU 散热有限，`--threads` 设为 2，不设更高值以免 CPU 过载关机。
2. **MinGW 依赖：** llama-cli 依赖 MinGW DLL（`libstdc++-6.dll` 等），脚本会自动将 `C:/Program Files/MinGW/mingw64/bin` 添加到 PATH。如果 MinGW 安装路径不同，需修改脚本中的 `_MINGW_BIN` 变量。
3. **编码处理：** 脚本使用 `-f`（文件方式）传入 prompt，避免 Windows 命令行中文编码问题。
4. **单轮模式：** 脚本使用 `--single-turn` 确保 llama-cli 在生成一次响应后退出，避免进入交互模式导致子进程挂起。
5. **CSV 追加模式：** 多次运行会追加数据到同一 CSV，不会覆盖已有记录。
