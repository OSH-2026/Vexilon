## 一、项目背景
随着万物互联（IoT）时代的到来，嵌入式设备对操作系统的要求已从单纯的“轻量级”转向“安全性”与“智能化”。
* **LiteOS**：华为 [LiteOS](https://gitee.com/LiteOS/LiteOS/)是华为技术有限公司于 2015 年发布的面向 IoT 领域的轻量级开源实时操作系统，遵循 BSD-3-Clause 开源协议。LiteOS 具备极致轻量（内核最小约 6 KB）、优先级抢占式实时调度、多种低功耗管理、模块化裁剪以及对 ARM Cortex-M/A、RISC-V 等主流嵌入式处理器的广泛支持等核心特性。LiteOS 在华为 HiLink、工业互联网等产品线中得到大规模部署，代码库约 40 余万行，全部以 C 语言编写，并与华为云 IoT 平台深度整合，支持 NB-IoT、LoRa、Wi-Fi 等多种连接协议。
* **Rust**：Rust 是由 Mozilla Research 主导、于 2015 年发布 1.0 版本的系统级编程语言。其核心设计目标是在不引入运行时垃圾回收的前提下，通过编译期静态分析（所有权、借用、生命周期）保证内存安全和线程安全。Rust 已连续八年位居 Stack Overflow 开发者调查「最受喜爱编程语言」榜首。Linux 内核自 6.1 版本起引入 Rust 作为第二开发语言，Android 开源项目中因引入 Rust 使内存安全漏洞数量显著下降。Rust 的 core 与 alloc 库支持无操作系统环境（no_std）开发，为嵌入式系统移植提供了完善的基础。
* **AI Agent 与 WASM 沙箱的融合**：与此同时，AI Agent 领域在 2025–2026 年经历了从"聊天工具"到"自主执行"的范式转变。以 IronClaw 为代表的新一代 AI Agent 框架，不再只是封装 LLM 的 HTTP 客户端，而是具备完整的工具调用体系、安全沙箱隔离和自动化执行能力。
  **IronClaw**（`github.com/nearai/ironclaw`）是 nearai 开源的、以 Rust 编写的安全 AI 助手框架，其核心设计哲学是"你真正可以信赖的 AI 助手"。其关键特性包括：

  - **WASM 沙箱**：所有不受信任的工具运行在隔离的 WebAssembly 容器中，采用基于能力（capability-based）的权限模型。工具代码对宿主机的访问必须经过白名单、泄露扫描、凭据注入等多层安全检查。
  - **WASM 工具（Tools）**：用户可以用 Rust 编写工具，编译为 `wasm32-wasip2` 格式，部署到 `~/.ironclaw/tools/`，Agent 即可自动调用；
  - **WASM 渠道（Channels）**：以 WASM 组件形式扩展通信渠道，目前支持 Telegram、Slack 等；
  - **多渠道接入**：REPL、HTTP webhook、Web 网关（SSE/WebSocket）等；
  - **Routines**：Cron 调度、事件触发器、Webhook 处理器，实现后台自动化；
  - **持久化记忆**：混合全文搜索（FTS）+ 向量检索（RRF），提供长期记忆工作空间；
  - **LLM 后端无关**：支持 nearai、OpenAI、Anthropic、Ollama、AWS Bedrock 等多种推理后端。

## 二、立项依据

### 1、C 语言内存安全缺陷的内在局限
C 语言自 1972 年问世至今，长期主导操作系统与嵌入式系统开发，但其*信任程序员*的设计哲学在现代复杂系统中暴露出严重的系统性缺陷。[微软 2019 年的安全分析报告](https://www.microsoft.com/en-us/msrc/blog/2019/07/we-need-a-safer-systems-programming-language)指出，其近 12 年中约 70% 的安全漏洞源于内存安全问题；[Google 的 Project Zero 数据](https://projectzero.google/)同样显示，Android、Chrome 等项目中大量 CVE 漏洞均与 C/C++ 内存管理失误直接相关。对于 LiteOS 而言，缓冲区溢出、释放后使用（UAF）、空指针解引用、数据竞争以及整数溢出等问题在 C 语言层面无法从根本上消除，只能依赖开发规范、代码审查和运行期检测工具加以缓解，而这些手段对资源受限的嵌入式设备尤其不适用。

### 2、IoT 安全形势的迫切需求
[国家标准 GB/T 36951-2018《信息安全技术 物联网感知终端应用安全技术要求》](http://c.gb688.cn/bzgk/gb/showGb?type=online&hcno=8D71779F7E6DB4B0368C22F7BE32FF1D&request_locale=zh)及 [ETSI EN 303 645](https://www.ul.com/zh-hans/resources/etsi-en-303-645-heguifuwuzhinan) 等国际标准明确要求物联网设备具备抵御常见网络攻击的能力。美国 CISA 发布的《安全设计原则》（Secure by Design）将「采用内存安全语言」列为推荐实践。欧盟《网络弹性法案》（Cyber Resilience Act）于 2024 年正式生效，要求联网产品制造商承担安全责任。在此背景下，以 Rust 改写 LiteOS 并引入 IronClaw 能力安全框架，是响应监管要求、提升产品安全竞争力的主动举措，具有切实的工程立项意义。

### 3、Rust 在嵌入式与内核领域的成熟度
Rust 在嵌入式与操作系统领域的生态已趋于成熟。core 库完全不依赖操作系统，alloc 库仅需自定义分配器即可使用，满足无 OS 环境的嵌入式开发需求。embedded-hal 提供跨平台硬件抽象层接口，覆盖 SPI、I2C、UART、GPIO 等常用外设；cortex-m 与 riscv crate 提供对主流嵌入式处理器的底层访问支持；RTIC 框架提供基于 Rust 类型系统的并发任务调度，与 LiteOS 的任务管理模型高度契合。[Tock OS](https://github.com/tock/tock) 与 [Hubris](https://github.com/oxidecomputer/hubris) 两个成功的 Rust 嵌入式操作系统项目证明了全 Rust 内核在资源受限平台上的工程可行性。

### 4、国产开源生态的现代化
基于 Gitee 上的 LiteOS 进行 Rust 化改造，不仅是对现有优秀架构的继承，更是对国产嵌入式生态在先进技术方向上的探索。IronClaw（作为 OpenClaw 生态的 AI 工具）能够为内核提供基于行为树或强化学习的决策支持，使 LiteOS 能够从传统的“静态配置”演进为“动态自适应”。

## 三、前瞻性分析
* **前瞻性**：目前工业界（如 Linux 内核、Android、Windows）都在积极引入 Rust。在 RTOS 领域，结合 AI 模型（IronClaw）进行内核级的资源调度与安全审计，代表了下一代“自愈型操作系统”的发展方向。
* **重要性**：
    * **高可靠应用**：在医疗、航天等容错率极低的领域，内存安全是底线。
    * **边缘智能**：IronClaw 的引入让 OS 能够智能识别异常流量或预测任务负载，实现真正的边缘侧智能。

### 1、技术趋势
当前，以内存安全为核心竞争力的系统编程语言正深刻改变基础软件的技术格局。在国家战略层面，美国 NSA 于 2022 年发布[技术报告](https://media.defense.gov/2022/Nov/10/2003112742/-1/-1/0/CSI_SOFTWARE_MEMORY_SAFETY.PDF)，明确建议政府机构和关键基础设施供应商迁移至内存安全语言；在操作系统层面，Linux 6.1、Android 13 以上版本均已引入 Rust 开发，Windows 团队亦公开表示部分内核组件正用 Rust 改写；在嵌入式生态层面，Zephyr RTOS 等已启动 Rust 支持计划。在此宏观背景下，以 Rust 改写 LiteOS 具有重要的前瞻战略价值，是 LiteOS 长期演进路线中不可回避的技术方向。
### 2、AI 与操作系统深度融合
自然语言 → 内核实验的完整闭环，是 AI for Systems 方向的前沿实践。
核心工作流程如下：

```
用户说一句话
   ↓
IronClaw AI Agent 理解意图
   ↓
自动生成 WASM 工具代码（Rust → wasm32-wasip2）
   ↓
WASM 工具在 IronClaw 沙箱中运行
   ↓
WASM 工具通过「LiteOS-IronClaw Bridge」调用编译好的 LiteOS 内核接口
   ↓
收集内核执行结果
   ↓
生成 research report（性能报告、行为分析等）
```
### 3、工业与学术双重价值
从工业界角度，本项目成果可直接服务于华为及其产业链在 IoT 产品安全合规方面的需求，以及工业互联网、车联网、医疗设备等高安全性 IoT 应用场景，并可作为开源社区的技术贡献推动国产 RTOS 的 Rust 生态建设。从学术界角度，本项目提供了大规模 C 语言系统向 Rust 迁移的方法论探索、能力安全模型在实际 RTOS 中的落地验证。

### 3.2 各项目详述

#### 3.2.1 OSH-2019：x-rust-freertos

**项目地址**：`https://github.com/OSH-2019/x-rust-freertos`

**改写对象**：FreeRTOS（广泛使用的嵌入式实时操作系统）

**已改写的内容**：
- 使用智能指针实现的双向链表（Rust 中这并不简单）
- 基于优先级的任务调度器（fully-functional task scheduler）
- 固定长度队列（fixed-length queue）
- 基于队列构建的信号量（semaphore）与互斥量（mutex）
- 一套可选编译的功能集，供用户定制内核

**主要经验与结论**：
- 证明了 Rust 改写 RTOS 核心调度逻辑的可行性；
- Rust 中实现双向链表等数据结构需要使用 `Rc<RefCell<T>>` 等智能指针，代码复杂度高于 C；
- 未涵盖的模块：定时器（timers）、事件组（event groups）、流缓冲区（stream buffers）、软件定时器守护任务、内存堆管理（heap_1~heap_5）、协程（co-routines）等。

#### 3.2.2 OSH-2023：imagination

**项目地址**：`https://github.com/OSH-2023/imagination`

**改写对象**：FreeRTOS（在 2019 届基础上继续推进）

**已改写的内容**：
- `list.c`（FreeRTOS 链表，基础数据结构）
- `task.c` 的全局变量部分
- `queue.c`（队列）
- 独立的 MMU 实验模块（基于 RISC-V 或 ARM）
- 尝试使用 `bindgen` 将 Rust 与 C 模块链接

**主要经验与结论**：
- FreeRTOS 中 C 语言的指针运算、类型转换在 Rust 中改写难度较高，尤其是 `void *` 指针和 `volatile` 关键字的处理；
- 命名方法和改写模板的统一对团队协作至关重要；
- 编译链接阶段（尤其是 C/Rust 混合编译）是主要瓶颈；
- **未完成/未涉及**：`timers.c`、`event_groups.c`、`stream_buffer.c`、`croutine.c`、heap 分配器系列，以及对 FreeRTOS 在真实嵌入式硬件（如 STM32、ESP32）上的完整运行验证。

#### 3.2.3 OSH-2023：Actus_Neopiritus

**项目地址**：`https://github.com/OSH-2023/Actus_Neopiritus`

**改写对象**：不是改写已有 C 系统，而是基于 **ArceOS** 框架（rcore-os 社区的实验性组件化 Rust OS）构建定制化操作系统内核。

**工作内容**：
- 基于 arceos 的组件化设计理念，研究如何用 Rust 的丰富语言特性设计相互独立的 OS 内核组件（如调度模块、内存模块、驱动模块）；
- 探索"让领域操作系统易于定制/开发/复用"的技术路径；
- 实践了组件化 OS 的可行性，参考了全国大学生计算机系统能力大赛相关命题。

**主要经验与结论**：
- Rust 在构建组件化、类型安全的 OS 框架方面具有独特优势；
- arceos 提供的 crate 依赖体系使得不同功能模块的组合和替换较 C 语言更清晰；
- 这与传统的"将 C 改成 Rust"路径不同，而是从零开始用 Rust 设计，适合探索架构创新而非渐进迁移。

#### 3.2.4 OSH-2024：RushToLight

**项目地址**：`https://github.com/OSH-2024/RushToLight`

**改写对象**：**OpenHarmony LiteOS-M 内核**（华为鸿蒙 IoT 操作系统，面向资源受限的 IoT 设备，源码：`gitee.com/openharmony/kernel_liteos_m`）

**已改写的内容**：
- `liteOS-M/kernel/src/mm/memory.c`（内存管理模块，LiteOS-M 内存堆的分配、释放等操作）
- 建立了 C/Rust 混合内核的工程结构（`liteOS-M/rust_kernel/`）

**主要经验与结论**：
- LiteOS-M 的内存管理模块存在明显的指针安全隐患（裸指针操作、双重释放风险等），是 Rust 改写的典型价值场景；
- 空指针改写是主要难点，`Option<NonNull<T>>` 是对应 C 空指针的惯用 Rust 写法；
- C/Rust 混合编译的工具链配置（交叉编译目标三元组、no_std 环境）是前期主要障碍；
- **已改写范围有限**，主要集中于 `memory.c` 一个文件。
- **未涉及**：`task.c`（任务管理）、`ipc/`（进程间通信：互斥量、信号量、消息队列、事件）、`sched/`（调度器）、`los_init.c`（内核初始化）等关键模块。

#### 3.2.5 OSH-2024：mkdir

**项目地址**：`https://github.com/OSH-2024/mkdir`

**改写对象**：**Linux 内核 bpf_trace 模块**（`kernel/trace/bpf_trace.c`，约 3500 行 C 代码）

**已改写的内容**：
- `kernel/trace/bpf_trace.c` 全文（改写后约 5000 行 Rust）
- 包括结构体改写、函数改写、内核宏的 Rust 等价实现、内核数据类型的绑定

**主要经验与结论**：
- 证明了将 Linux 内核非核心子系统模块用 Rust 改写的可行性；
- 原始 C 代码约 3500 行，改写为 Rust 后约 5000 行，代码量增长约 43%，这与 Rust 更显式的错误处理、类型声明有关；
- 结构体定义统一、函数库引用统一是工程协作的核心问题；
- 交叉编译（针对内核目标架构）和内核测试环境搭建是主要挑战；
- **改写完成度**：全文改写完成，但与真实 Linux 内核构建系统（KBuild）的集成和完整功能测试仍有未尽工作。
- **未涉及的 Linux 子系统**：VFS 层、内存管理（`mm/`）、调度器（`kernel/sched/`）、网络协议栈（`net/`）、文件系统（`fs/ext4`、`fs/btrfs` 等）。

#### 优先级 ★★★（核心，价值最高）

**`los_task.c` — 任务管理**

这是内核最核心的文件，负责任务的创建、删除、挂起、恢复、延时等全部生命周期操作。C 代码中充斥着裸指针操作（任务控制块 TCB 的链表挂接、栈指针操作），是内存安全漏洞的重灾区。Rust 改写后，任务句柄可以用 `NonNull<LosTaskCB>` 或索引替代裸指针，生命周期错误在编译期就能被捕获。

**`los_sched.c` — 调度器**

基于优先级的抢占式调度器，维护就绪队列和当前运行任务。与 `los_task.c` 高度耦合，建议两者一起改写。调度器中的全局状态（当前任务、就绪位图）可以用 Rust 的 `static Mutex<T>` 或 `AtomicUsize` 安全封装。注意：上下文切换本身（寄存器保存/恢复）在 `arch/` 目录下，需要内联汇编，属于 unsafe 的合理边界。

**`los_sortlink.c` — 排序链表**

这是调度器和软件定时器共用的底层数据结构（按超时时间排序的链表），是一个相对独立、边界清晰的模块，非常适合作为改写的**起点**。代码量小（几百行），但对指针正确性要求高，Rust 改写价值明显。

---

#### 优先级 ★★（IPC 模块，独立性强）

**`los_sem.c` — 信号量**，**`los_mux.c` — 互斥锁**，**`los_queue.c` — 消息队列**，**`los_event.c` — 事件标志组**

这四个文件共同构成 LiteOS-M 的 IPC（进程间通信）子系统。它们的特点是：

- 相互之间耦合较低，可以分别独立改写；
- 每个文件代码量适中（300~800 行 C），单个人改写一个学期内可以完成；
- 都涉及阻塞/唤醒操作（修改任务状态 + 触发调度），天然存在竞态条件风险，是 Rust 类型安全的典型受益场景；
- 互斥锁中的**优先级继承**（priority inheritance）机制在 C 中尤其容易出错。

---

#### 优先级 ★（较难或相对次要）

**`los_swtmr.c` — 软件定时器**

基于 `los_sortlink.c` 的软件定时器，提供定时回调功能。依赖排序链表和调度器，建议在 `los_sortlink.c` 改写完成后再处理。

**`los_tick.c` — Tick 时钟**

Tick 中断处理，代码量极小，但与硬件中断直接挂钩，需要 `unsafe` 处理中断上下文。可作为小型"热身"模块。

**`los_membox.c` — 静态内存池**

静态内存池（固定大小块分配），与已改写的 `los_memory.c`（动态内存）是兄弟模块，逻辑类似但更简单，改写难度较低，适合作为接续 2024 届成果的第一步。

**`los_init.c` — 内核初始化**

内核启动入口，把所有模块串联起来初始化。这个文件本身代码量不大，但它的正确性依赖所有其他模块已经改写完毕，最后处理。

## 五、现有缺点 (基于原版 C-LiteOS)

### 1、内存安全缺陷
LiteOS 以 C 语言实现，在以下关键子系统中存在潜在的内存安全风险，且这些风险在 C 语言层面无法从语言机制上彻底消除：
#### (1)内核堆内存管理器
LiteOS 实现了多种内存分配算法（bestfit、bestfit_little、tlsf、dlink），其核心分配/释放逻辑以裸指针操作为主。双重释放（double-free）可能导致堆元数据损坏，进而引发任意代码执行；内存碎片处理中的指针运算错误可导致越界写；回调钩子（mem_module_hook_t）的生命周期管理依赖人工规范而非语言机制保证，易引入悬挂指针。
#### (2)任务调度器
任务控制块（LosTaskCB）通过全局指针数组管理，任务创建/删除过程中的竞态条件若处理不当，可在多核场景（SMP）下引发数据竞争。任务栈溢出检测仅依赖栈水位线机制，不能防止溢出本身的发生，溢出可能覆盖相邻任务控制块数据结构，导致系统崩溃或被利用。
#### (3)网络协议栈与设备驱动
LiteOS 集成的轻量级 TCP/IP 栈（lwIP）和设备驱动代码中，报文长度字段的整数溢出、输入缓冲区的边界检查遗漏等问题在历史 CVE 记录中均有体现，是远程代码执行（RCE）的高风险区域，直接威胁物联网设备的安全态势。

### 2、并发安全缺陷
LiteOS 支持 SMP 和抢占式调度，其并发安全完全依赖人工使用互斥锁（mutex）、自旋锁（spinlock）等同步原语。开发者可能遗漏对共享数据结构的加锁保护，而编译器不提供任何检查；在中断处理程序中访问可能阻塞的内核对象属于未定义行为，但 C 编译器无法检测此类错误；实时任务因低优先级任务持有共享锁而被阻塞，影响实时性保证（优先级反转问题）。这些问题在 SMP 多核场景下尤为突出，且极难通过测试发现和调试。

### 3、访问控制与权限管理缺陷
LiteOS 的访问控制模型较为简单，不具备细粒度的资源访问管控能力。任意任务均可调用全部内核 API，无法限制任务对特定硬件外设的访问；LiteOS 设计上以单一特权级运行（MPU 隔离为可选配置），一旦某个任务的代码存在漏洞，可直接威胁整个系统安全；多个任务可同时操作同一外设寄存器，依赖开发约定而非机制保证；系统缺乏内置的安全事件日志与异常访问检测机制，事后溯源困难。

## 六、改进后预期优点
### 1、内存安全的编译期保证
以 Rust 重构后，原有 C 代码中的内存安全问题将从根本上被消除或管控。Rust 的所有权系统确保同一时刻每个内存对象恰有一个所有者，从机制上消除释放后使用（UAF）和双重释放（DF）；借用检查器强制的借用规则在编译期消除数据竞争；生命周期注解机制确保引用有效性在编译期得到验证，从语言层面消除悬挂指针。必要的硬件访问封装于有限的、经过严格审查的 unsafe 块中，便于集中安全审计。根据现有 Rust OS 项目（如 Tock OS、Android Rust 模块）的实践数据，采用 Rust 改写后，内存安全相关漏洞预期减少 70% 左右。
