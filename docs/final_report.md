## 1. 项目介绍

本项目为中国科学技术大学 2026 春季学期 OSH 操作系统课程设计 Vexilon 团队项目，延续 2024 届 RushToLight 团队对 LiteOS-M 动态内存模块（los_memory.c）的 Rust 改写工作，在此基础上继续探索 LiteOS-M 内核中更多关键模块的 Rust 化实现。

项目围绕 OpenHarmony LiteOS-M 轻量级实时操作系统展开，重点关注 C 语言内核中常见的裸指针、手动资源管理、弱类型接口和并发状态维护等问题。我们采用 Rust no_std + alloc 与 C 混合开发的方式，对任务管理、调度器、时钟节拍、有序链表、内存块管理等模块进行重构与适配，并通过交叉编译、模块测试和上板 Demo 对功能兼容性进行验证。

在硬件验证部分，项目使用正点原子 ALIENTEK M144Z-M4 最小系统板完成 EcoPet 嵌入式演示程序。该开发板搭载 STM32F407ZGT6 芯片，板卡标注资源包括 1MB Flash、192KB RAM、8Mb SRAM、128Mb SPI Flash，并提供 USB UART、USB Slave/Host、LCD/TF Card 接口、10 组扩展接口、2 个按键、2 个 LED 和 2Kb EEPROM 等外设资源。EcoPet 实际使用 USART1 串口完成 PC 与开发板通信，使用 LiteOS-M 多任务和消息队列组织宠物状态机，并通过板载 PF9/PF10 LED 做状态提示，从而验证任务调度、队列通信、时序管理和基础硬件联动能力。

项目初期曾计划使用 IronClaw 作为安全接口层，但在实际适配中遇到ironclaw官方仓库依赖缺失、维护状态不稳定和嵌入式端资源开销偏大的问题。最终方案改为：板端固件负责严格的指令解析、参数范围检查和状态钳位，PC 端使用 Ollama + Qwen3:8B 的 Python Agent 负责自然语言到串口指令的转换、板端响应解释和低值告警提示。这个替代方案没有保留 IronClaw 的 WASM 沙箱能力，但能够覆盖本课程项目的主要验证目标，并且更容易在现有硬件和离线环境中落地。

## 2. 选题背景与研究意义

### 2.1 嵌入式操作系统安全现状

随着物联网IoT设备的大规模普及，轻量级实时操作系统（RTOS）已广泛应用于智能家居、工业控制、车载设备、智能穿戴等数十亿终端场景。OpenHarmony LiteOS-M作为华为开源的轻量化嵌入式内核，凭借体积小、资源占用低、多芯片架构适配、生态丰富的优势，成为IoT终端的主流操作系统内核。

但当前主流嵌入式内核均基于C语言开发，原生存在难以规避的系统性安全缺陷。根据微软、谷歌等机构的安全报告，其项目中大量系统漏洞源于C语言内存管理缺陷，包括空指针解引用、缓冲区溢出、内存泄漏、双重释放、悬挂指针等问题。嵌入式设备因资源受限、缺乏成熟的内存保护机制，安全风险更为突出。

### 2.2 传统C语言LiteOS-M内核核心痛点

原生C语言实现的LiteOS-M内核存在三大不可忽视的短板，也是本项目重点优化的方向：

**（1）内存安全缺陷**：内核内存块管理、任务控制块、有序链表等核心结构依赖裸指针操作，无编译期安全校验，越界访问、悬挂指针、内存碎片堆积问题频发，且缺乏强类型约束，人工编码极易引入隐性漏洞。

**（2）并发安全缺失**：多任务调度、任务队列操作的并发控制主要依赖人工锁管理，竞争访问、资源抢占等问题无法在编译期检测，多任务运行场景下易出现系统卡死、任务异常退出等问题。

**（3）调用安全无保障**：用户层与内核层交互接口无统一规范，参数校验、权限校验缺失，弱类型参数传递易引发非法调用、参数溢出等安全风险，内核边界防护能力薄弱。

### 2.3 Rust重构的行业趋势与价值

当前全球操作系统领域已全面开启Rust安全迭代趋势：Linux内核5.20正式接入Rust支持、Windows内核逐步用Rust替换C++核心模块、美国CISA机构发布《内存安全路线图指南》，明确将C/C++列为高风险内存不安全语言，推荐Rust作为系统级开发替代语言。

Rust凭借**编译期内存安全校验、所有权与借用机制、零运行时开销、无垃圾回收、强类型系统**的主要优势，适配嵌入式实时系统的性能与安全需求。相较于往届仅重构内存模块的探索性工作，本项目对任务、调度、时钟等关键运行模块的Rust化重构，能够改善嵌入式内核的内存安全问题，同时保留LiteOS-M轻量、实时的核心特性，具有一定的工程实践参考价值。

## 3. 技术选型与迭代依据

### 3.1 迭代基础：继承往届成果，扩展验证范围

2024 届 RushToLight 团队已完成 LiteOS-M `los_memory.c` 动态内存模块的 Rust 改写，证明了在 LiteOS-M 中引入 Rust 模块具备可行性。本项目在该基础上继续向任务、调度、时钟和基础数据结构等运行链路推进，目标不是一次性替换完整内核，而是在保持 C/Rust 接口兼容的前提下，验证更多核心模块的 Rust 化改造路径。

与往届工作相比，本项目增加了三类内容：第一，扩大 Rust 重构模块范围；第二，补充跨语言编译、链接和测试流程；第三，加入 STM32F407 上板 Demo 与 PC 端自然语言 Agent，用更接近真实使用的方式观察内核任务、队列和串口交互行为。

### 3.2 核心技术栈选型

**开发语言**：Rust（no_std + alloc）与 C 混合开发。Rust 用于重构内核模块，C 用于保留 LiteOS-M 原有启动、硬件适配和部分驱动逻辑。

**编译工具链**：Cargo、bindgen、cbindgen 与 GCC 工具链配合使用，用于生成 Rust 静态库、C/Rust 绑定和最终链接产物。

**硬件平台**：STM32F407ZGT6 开发板。项目工程目录沿用 `stm32f429ig_firechallenger` 命名，但本次固件适配重点是 F407 的 RAM、栈顶和 84MHz 时钟配置。

**上板 Demo**：EcoPet 电子宠物程序。Demo 使用 USART1、LiteOS-M 任务、消息队列、定时衰减逻辑和 LED 指示，验证多任务调度、队列通信、串口中断接收和状态机运行。

**智能交互**：最终未采用 IronClaw。PC 端改用 Ollama + Qwen3:8B 与 Python 串口程序实现自然语言交互；板端仍以固定串口协议为可信边界，负责最终参数校验和状态更新。

### 3.3 重构模块优先级选型依据

结合 LiteOS-M 内核结构和课程项目工作量，本项目选择了五个与调度、计时和内存管理关系较紧密的模块作为重构对象：

1. **los_sortlink.c（有序链表）**：为延时队列、定时器队列等提供基础数据结构，指针操作集中，适合验证 Rust 封装链表节点和边界检查的效果；

2. **los_tick.c（时钟节拍）**：提供系统节拍计数和超时判断，是任务延时与调度时序的基础；

3. **los_membox.c（内存块管理）**：用于小块内存分配，适合验证 Rust 对边界校验、重复释放检查和状态统计的改造方式；

4. **los_task.c（任务管理）**：涉及任务创建、状态切换和资源维护，是观察 C/Rust 混合接口兼容性的重要模块；

5. **los_sched.c（任务调度）**：负责就绪队列、优先级和任务切换逻辑，是本项目验证多任务运行行为的重点模块。

## 4. LiteOS-M核心模块原理与原生C语言痛点分析

### 4.1 有序链表模块（los_sortlink）原理与痛点

有序链表是LiteOS-M内核的基础通用数据结构，广泛应用于任务延时队列、定时器队列、事件等待队列等场景，通过节点指针排序实现有序存储与快速检索。原生C语言实现依赖手动指针赋值、节点挂载与卸载，无类型校验，存在空指针访问、节点重复挂载、链表断链、野指针残留等问题，极易引发内核调度异常。

### 4.2 时钟节拍模块（los_tick）原理与痛点

Tick时钟是嵌入式实时系统的心跳核心，通过定时中断驱动系统节拍计数，为任务超时、定时器触发、调度时机判断提供时间基准。原生C语言实现的节拍计数、中断处理逻辑依赖全局变量与裸指针传递，并发中断场景下易出现计数错乱、节拍溢出、中断嵌套冲突等问题，无编译期防护。

### 4.3 内存块管理模块（los_membox）原理与痛点

Membox模块是LiteOS-M精细化内存分配单元，针对小内存块场景优化分配效率，弥补全局内存池的性能短板。原生C语言实现存在内存块边界校验缺失、重复释放检测薄弱、内存碎片统计不准确等问题，长期运行易导致内存资源耗尽、系统稳定性下降。

### 4.4 任务管理模块（los_task）原理与痛点

任务管理模块负责内核任务的创建、初始化、状态切换、资源回收，是多任务操作系统的核心。原生C语言任务控制块（TCB）通过裸指针管理任务堆栈、优先级、状态信息，存在任务资源泄漏、堆栈越界、无效任务指针访问、多任务状态竞争等安全隐患，人工锁机制无法减少并发问题。

### 4.5 调度器模块（los_sched）原理与痛点

调度器基于任务优先级与就绪状态，通过有序链表筛选最高优先级任务，实现任务抢占式调度。原生C语言调度逻辑依赖大量条件判断与指针遍历，调度链表更新、任务就绪/阻塞状态切换过程中，易出现链表节点篡改、优先级错乱、任务饿死等问题，且错误难以定位调试。

## 5. 基于 Rust 的内核多模块重构方案与实现

本项目沿用往届 Rust 重构 LiteOS-M 模块的基本路线，在保持原有 C 接口和数据布局的前提下，将部分内部逻辑迁移到 Rust 实现。重构重点不是简单追求“全 Rust”，而是在可编译、可链接、可测试的约束下，逐步减少裸指针直接操作、补充边界检查，并让模块行为尽量与原生实现保持一致。

### 5.1 核心重构技术方案复用与优化

**（1）bindgen 头文件自动绑定**：使用 bindgen 将 C 侧结构体、宏定义和函数声明映射到 Rust 侧，减少人工翻译导致的字段偏移和类型不一致问题。

**（2）cfg + feature 条件编译适配**：通过 Rust 的 cfg 属性和 Cargo feature 对齐 LiteOS-M 中已有的条件编译开关，使同一模块能够适配不同配置。

**（3）显式空值与错误处理**：在 Rust 内部尽量使用 Option、Result 和封装函数表达空值与错误返回。对于必须经过 FFI 的裸指针，则集中在少量 `unsafe` 边界中检查，避免在业务逻辑中到处分散处理。

**（4）`#[repr(C)]` 结构体布局适配**：对跨语言共享的数据结构使用 C 兼容布局，降低 C/Rust 之间字段顺序、对齐方式和大小不一致的风险。

**（5）`#[no_mangle]` 函数导出**：对外暴露与 C 侧可链接的稳定符号，使原有 LiteOS-M 调用点可以在较少改动下接入 Rust 实现。

### 5.2 各模块 Rust 重构实现

本项目对五个模块分别完成 Rust 版本实现和接口适配。由于 LiteOS-M 内核仍包含大量 C 代码，且 FFI 边界需要使用 `unsafe`，因此本项目的安全收益主要体现在“减少常见误用、增强边界检查、改善可维护性”，而不是宣称消除所有内存安全问题。

#### 5.2.1 有序链表模块 los_sortlink.rs 重构实现

有序链表用于任务延时队列、定时器队列等场景。原 C 实现依赖手动维护前驱、后继和 key 值，出错时可能导致重复挂载、断链或空指针访问。

Rust 版本主要改动包括：

1. 将链表节点操作封装为统一接口，减少外部代码直接修改节点指针的机会；
2. 对插入、删除、查询等入口补充参数检查；
3. 对空链表、重复删除、无效链表类型等场景给出明确返回；
4. 保留按 key 升序插入和超时节点查询等原有行为，保证上层调度与定时逻辑可继续使用。

#### 5.2.2 系统时钟节拍模块 los_tick.rs 重构实现

Tick 模块为任务延时、超时判断和调度时机提供时间基准。Rust 版本保留原有接口语义，并对计数更新、单位换算和边界值处理进行了整理。

主要改动包括：

1. 对系统 tick 计数和换算逻辑进行封装，减少全局状态被随意修改的风险；
2. 对毫秒、tick、纳秒等单位换算补充边界检查；
3. 保持与任务延时、软件定时器等上层模块的接口兼容；
4. 在测试中覆盖连续递增、边界值和多轮更新场景。

#### 5.2.3 精细内存块管理模块 los_membox.rs 重构实现

Membox 用于固定大小内存块分配。原 C 实现中，内存块头部、空闲链表和释放状态都需要人工维护，容易受到越界写、重复释放和跨池释放影响。

Rust 版本主要改动包括：

1. 在分配、释放入口集中检查内存池和块地址合法性；
2. 对重复释放、非法地址释放和空指针参数返回错误；
3. 保留内存池状态统计接口，便于测试和调试；
4. 尽量维持固定块分配的轻量特性，不引入复杂运行时依赖。

#### 5.2.4 任务管理模块 los_task.rs 重构实现

任务管理模块负责任务创建、挂起、恢复、删除和优先级维护。Rust 版本围绕任务状态流转和参数检查做了适配。

主要改动包括：

1. 将部分任务状态转换逻辑整理为更集中的状态处理路径；
2. 对任务创建参数、任务 ID、优先级范围等入口进行校验；
3. 保留原有任务优先级、堆栈配置和调度策略；
4. 通过测试覆盖创建、挂起、恢复、删除和非法参数场景。

#### 5.2.5 调度器模块 los_sched.rs 重构实现

调度器负责就绪队列维护、优先级选择和任务切换触发。Rust 版本重点整理了调度状态更新路径，并与有序链表模块配合验证。

主要改动包括：

1. 通过封装接口维护就绪队列，减少多个位置重复修改调度状态；
2. 对任务入队、出队、挂起恢复和优先级修改后的状态同步进行检查；
3. 保留 LiteOS-M 原有优先级抢占和空闲任务兜底思路；
4. 在测试中覆盖空调度、最高优先级筛选和最小超时时间获取等场景。

#### 5.2.6 跨模块兼容保障

为保证多模块 Rust 重构后仍能与原 LiteOS-M 工程协同工作，项目采用以下约束：

1. 跨语言共享结构体使用 `#[repr(C)]`；
2. 对外接口使用 `#[no_mangle]` 暴露稳定符号；
3. 使用 bindgen/cbindgen 管理 C/Rust 绑定，减少手写声明；
4. 采用分模块替换策略，先保证单模块测试通过，再进行跨模块联动；
5. 对 FFI 边界保留必要 `unsafe`，并把检查逻辑集中在入口处，降低维护成本。

## 6. C/Rust 混合编译与 FFI 通信实现

LiteOS-M 原工程以 C 语言为主，本项目的 Rust 模块需要与原有启动流程、硬件驱动、中断处理和测试代码协同工作。因此，混合编译与 FFI 适配是项目能否落地的关键环节。

### 6.1 混合编译环境搭建

项目基于 Linux/WSL 开发环境和交叉编译工具链完成 Rust 静态库构建，再与 C 侧 LiteOS-M 工程链接。Rust 侧使用 no_std + alloc 模式，避免依赖桌面标准库；C 侧继续保留原有硬件初始化、串口输出和中断相关代码。

在单元测试阶段，项目先针对模块接口进行主机侧或交叉编译测试；在上板阶段，则将通过测试的模块接入固件 Demo，观察任务、队列、时钟和串口链路是否能够正常协作。这个流程更接近“逐步替换和验证”，而不是一次性整体替换。

### 6.2 标准化混合编译流程

整体流程如下：

**第一步：Rust 模块编译**：通过 Cargo 将重构模块编译为静态库，导出 C 侧需要调用的符号；

**第二步：绑定生成与接口检查**：使用 bindgen/cbindgen 生成或校验跨语言接口，确保函数签名、结构体布局和常量定义一致；

**第三步：C 工程链接**：在原 LiteOS-M 构建流程中链接 Rust 静态库，并保留必要的 C 侧硬件适配代码；

**第四步：测试与上板验证**：先运行模块测试，再通过 EcoPet Demo 验证多任务和串口联动行为。

### 6.3 C/Rust FFI 通信机制

本项目使用两类 FFI 调用：

**（1）C 调用 Rust**：C 侧通过稳定符号调用 Rust 实现的任务、调度、链表、时钟和内存块管理函数。Rust 函数对外保持 C ABI，内部再进行参数检查和状态更新。

**（2）Rust 调用 C**：Rust 模块在需要复用已有硬件接口、日志输出或内核基础函数时，通过 bindgen 生成的声明调用 C 函数。

需要注意的是，FFI 本身不能自动提供安全保证。项目通过减少裸指针分散使用、集中检查参数、保持结构体布局一致和增加测试覆盖来降低风险。这个设计使 Rust 模块能够嵌入原有 LiteOS-M 工程，同时保留后续继续替换其他模块的空间。

## 8. 智能交互体系迭代：从 IronClaw 到 Ollama + Qwen3

项目初期曾计划使用 IronClaw 作为安全中间接口层。IronClaw 的 WASM 沙箱和 capability-based 权限模型在设计上适合作为“用户输入到内核操作”之间的隔离层，因此早期报告和方案中曾围绕它展开设计。

实际推进时，IronClaw 没有成为最终实现，主要原因有三点：

1. **依赖和维护风险**：ironclaw官方github仓库存在依赖缺失或维护状态不稳定，在本项目的 WSL/本地环境中难以完成稳定构建；
2. **资源与工程成本不匹配**：完整 Agent 运行时和 WASM 沙箱对 STM32F407 这类资源受限平台并不友好，裁剪到可上板状态需要额外投入；
3. **验证目标发生收敛**：本课程项目更需要验证 LiteOS-M 重构模块、任务调度、队列通信和串口交互链路，而不是实现完整的安全沙箱运行时。

因此，最终方案将安全边界放回板端固件：固件侧的 `ParseCommand` 只接受 `STATUS`、`FEED <1-100>`、`PLAY <1-100>`、`SLEEP`、`HEAL` 等明确指令，所有状态更新都经过 `clamp` 钳位到 `[0, 100]`，并通过错误码反馈非法命令或非法参数。PC 端的 Ollama + Qwen3:8B Agent 只承担自然语言翻译、板端响应解释和告警展示，不直接绕过固件协议修改内核状态。

这个替代方案牺牲了 IronClaw 预期中的 WASM 沙箱隔离能力，但带来了更直接的工程收益：依赖更少、部署更简单、离线可运行、与串口调试流程兼容，也不会影响 EcoPet Demo 对任务调度、队列通信、定时衰减和硬件状态指示的验证效果。

### 8.1 技术方案迭代原因与适配思路

Ollama + Qwen3 的定位不是替代内核安全机制，而是提升交互层可用性。Agent 将中文或英文自然语言转换为板端协议指令；板端负责最终合法性判断和状态更新；串口 telemetry 和 `WARN:*` 日志提供可观测性。这样可以把不确定的大模型输出限制在固定协议内，避免把模型结果直接当作可信内核操作。

### 8.2 Ollama + Qwen3 智能体系核心功能实现

1. **自然语言到指令转换**：`ecopet_agent_ollama.py` 通过 Prompt 将用户输入转换为 `STATUS`、`FEED`、`PLAY`、`SLEEP`、`HEAL` 等板端命令；无法识别时返回 `UNKNOWN`，避免随意下发无效文本；

2. **板端响应解释**：Agent 将 `OK:*`、`WARN:*` 和状态字段解释为中文描述，降低直接阅读串口日志的门槛；

3. **低值告警提示**：后台线程持续监听串口输出，遇到 `WARN:LOW_HEALTH`、`WARN:HIGH_HUNGER`、`WARN:LOW_MOOD`、`WARN:LOW_ENERGY` 时立即提示用户；

4. **调试兼容性**：用户仍可直接输入标准指令，便于在自然语言交互之外进行确定性调试。

## 9. 真机上板验证与 AI 智能代理联动实现

本项目在 STM32F407ZGT6 开发板上完成 EcoPet Demo 的基础上板验证。该 Demo 不是完整产品化应用，而是一个用于观察 LiteOS-M 多任务、消息队列、时钟节拍、串口中断和 GPIO 输出的综合测试场景。

### 9.1 真机部署环境搭建

固件工程位于 `LiteOS-M/on-board/liteos_f407/stm32f429ig_firechallenger/cortex-m4_stm32f429ig_firechallenger_gcc/`。虽然目录名保留了 F429 历史工程命名，本次提交中的链接脚本按 F407 的 128KB RAM 和 `_estack=0x20020000` 配置，系统时钟采用 HSI 16MHz 经 PLL 配置到 84MHz。串口使用 USART1，波特率为 115200，LED 使用 PF9 和 PF10。

### 9.2 EcoPet 智能交互案例实现

EcoPet 用于验证重构后内核模块在一个小型嵌入式业务中的协作情况。程序采用三任务结构：

1. `UartRxTask`：从 USART1 中断写入的环形缓冲区读取字符，按行解析命令，并将合法命令写入 LiteOS-M 队列；
2. `PetStateTask`：从队列读取命令，执行宠物状态机逻辑，并通过串口输出 `OK:*`、`WARN:*` 或 `ERR:*`；
3. `TelemetryTask`：每秒运行一次，累计到 10 秒后执行被动状态衰减，并持续输出低健康、高饥饿、低心情、低精力等告警。

状态机包含 `health`、`hunger`、`mood`、`energy` 四个字段。所有字段都限制在 `[0, 100]` 区间内，避免状态计算溢出。支持的命令包括：

- `STATUS`：查询当前状态；
- `FEED <1-100>`：降低饥饿值，低饥饿时大量喂食会触发 `WARN:OVERFED`；
- `PLAY <1-100>`：提升心情、消耗精力并增加饥饿值，包含 LCG 伪随机事件；
- `SLEEP`：恢复精力和部分健康；
- `HEAL`：恢复健康，但会小幅降低心情。

PLAY 指令中加入了随机增益和风险：心情、精力消耗、饥饿变化在 `[0, 30]` 范围内随机产生，另有 20% 概率触发受伤并扣除 `[5, 20]` 健康值。程序还加入 `ERR:PLAY_FATAL` 保护，避免在预测会导致死亡的情况下继续执行玩耍操作。

硬件联动方面，PF9 绿色 LED 表示心情较好，PF10 红色 LED 表示高饥饿、低健康或低精力等需要关注的状态。串口输出用于记录命令执行结果、状态字段、告警和错误信息，便于 PC 端 Agent 或串口工具观察。

### 9.3 AI 智能代理集成

PC 端脚本 `LiteOS-M/on-board/agent/ecopet_agent_ollama.py` 使用 Python 编写，依赖 `pyserial` 与本地 Ollama HTTP 接口。脚本默认连接 `COM5`、115200 波特率，并调用 `qwen3:8b` 模型完成两类转换：自然语言到板端指令、板端响应到中文解释。

#### 9.3.1 代理脚本整体架构与运行环境

Agent 采用主线程交互、后台线程监听串口的结构。后台线程持续读取板端输出，普通响应会保存在响应列表中，低值告警会立即打印。主线程接收用户输入，如果输入已经是标准命令则直接透传；否则调用 Qwen3 生成指令后再通过串口发送。

#### 9.3.2 核心功能实现

**（1）自然语言转板端控制指令**

脚本通过 Prompt 将“给宠物喂饭”“陪它玩一会”“先治疗再睡觉”等输入转换为一条或多条标准指令。模型输出不是最终可信操作，固件侧仍会检查命令名称和参数范围。

**（2）板端响应解释**

脚本把 `health`、`hunger`、`mood`、`energy` 等字段解释为中文描述，并根据 `OK`、`WARN`、`ERR` 前缀补充建议。这样可以保留串口日志的可调试性，同时让演示时的交互更直观。

**（3）主动告警显示**

当板端输出 `WARN:LOW_HEALTH`、`WARN:HIGH_HUNGER`、`WARN:LOW_MOOD`、`WARN:LOW_ENERGY` 时，后台线程会立即显示提醒，不需要用户主动查询状态。

**（4）异常处理**

脚本对串口连接失败、Ollama 请求异常、板端无响应等情况给出提示，避免交互程序直接退出。现阶段异常处理以演示和调试为主，后续还可以补充端口自动发现、重连和日志持久化。

### 9.3.3 人机交互运行流程

1. 启动脚本并连接串口；
2. 用户输入自然语言或标准指令；
3. Agent 将自然语言转换为板端协议指令；
4. 固件执行命令并通过串口返回状态；
5. Agent 展示原始板端输出，并给出中文解释；
6. 后台线程持续监听并显示低值告警。

### 9.3.4 代码落地价值

该 Agent 的价值主要体现在演示和调试体验上：它保留了标准串口指令的确定性，又允许用户用自然语言操作 EcoPet；它不改变固件侧安全边界，也不依赖云端服务，适合课程展示和本地离线调试。

## 10. 项目总结与核心成果

本项目在往届单一模块 Rust 改写的基础上，完成了更大范围的 LiteOS-M Rust 化探索，并补充了上板 Demo 与自然语言交互工具。主要成果如下：

1. **扩展 Rust 重构模块范围**：完成 `los_sortlink`、`los_tick`、`los_membox`、`los_task`、`los_sched` 五个模块的 Rust 化实现与接口适配，在往届内存模块工作的基础上覆盖更多运行链路；

2. **完善 C/Rust 混合编译路径**：通过 bindgen、cbindgen、`#[repr(C)]`、`#[no_mangle]` 和静态库链接方式，整理出 LiteOS-M 中 C/Rust 模块协同工作的基本流程；

3. **完成 EcoPet 上板 Demo**：在 STM32F407 上实现三任务架构、串口环形缓冲、LiteOS-M 队列、状态机、被动衰减和 LED 指示，验证重构模块能够支撑一个小型嵌入式应用；

4. **完成 IronClaw 方案迭代说明与替代实现**：项目没有继续使用 IronClaw，而是采用“固件侧固定协议与参数校验 + PC 端 Ollama/Qwen3 交互”的方案，更符合现有硬件资源和课程周期；

5. **实现 PC 端自然语言 Agent**：`ecopet_agent_ollama.py` 支持自然语言转指令、板端响应解释、后台告警监听和直接指令透传，提高了演示和调试效率；

6. **形成可复用的工程经验**：项目沉淀了模块选择、接口绑定、混合编译、单元测试、上板验证和报告修订中的经验，可为后续继续推进 LiteOS-M Rust 化提供参考。

## 11. 问题反思与解决方案

**问题 1：多模块耦合导致混合编译和链接复杂**：多个 Rust 模块同时替换时，容易遇到符号命名、结构体布局和链接顺序问题。项目采用分模块编译、逐步替换、统一导出接口的方式降低风险。

**问题 2：no_std 环境下可用工具有限**：嵌入式环境不能直接依赖标准库，部分数据结构、错误处理和内存分配逻辑需要重新适配。项目通过 `alloc`、轻量封装和保留必要 C 侧能力完成基础适配。

**问题 3：IronClaw 未能落地**：IronClaw 的依赖和资源要求与本项目周期、硬件平台不匹配。项目最终将安全边界放在固件协议层，把大模型限制为交互辅助组件，保证 Demo 能够稳定完成验证。

**问题 4：真机压力测试仍不充分**：当前上板验证以功能联动为主，尚未覆盖长时间运行、高频串口输入、极端任务负载和异常断连等场景。后续需要补充自动化压力测试与日志分析。

**问题 5：AI Agent 仍偏演示工具**：当前脚本默认串口和模型名固定，异常恢复能力有限。后续可以加入端口扫描、配置文件、重连机制和更明确的日志记录。

3. **完善轻量级安全接口层**：在不依赖 IronClaw 的前提下，基于 EcoPet 中已经实现的固定协议、参数校验和状态钳位，设计更通用的用户态到内核态调用约束；

4. **优化 Agent 工具链**：加入配置文件、串口自动发现、日志保存和模型降级策略，使其更适合复现实验和现场展示；

5. **量化性能与资源开销**：进一步测量 Rust 模块对代码体积、RAM 占用、调度延迟和串口响应时间的影响，为后续优化提供数据依据。

## 13. 结束语

Vexilon 项目在 RushToLight 团队工作的基础上，继续探索 LiteOS-M 内核 Rust 化的工程路径。项目没有把目标设定为一次性替换完整内核，而是选择若干关键模块进行重构，并通过 EcoPet Demo 验证任务、队列、时钟、串口和 GPIO 等链路的协同工作。

IronClaw 方案最终没有进入实现阶段，这是项目推进中的一次重要调整。通过将可信边界放在固件协议和参数校验上，同时使用 Ollama + Qwen3 改善 PC 端交互体验，项目在有限时间和硬件资源内完成了可演示、可调试的替代方案。

后续工作可以继续沿着两个方向推进：一是扩大 Rust 重构模块范围并补充量化测试；二是把 EcoPet 中形成的轻量协议、状态检查和 Agent 工具整理为更通用的嵌入式验证框架。这样可以让本项目不仅停留在一次课程 Demo，也为后续类似 LiteOS-M Rust 化实验提供可复用的基础。
